# 架构说明

## 核心职责原则

凡是不依赖某个游戏进程就能完成的能力，都归 Harness 插件负责。游戏适配器只负责必须调用该游戏运行时或游戏 API 的工作。

| Harness 插件 | 游戏适配器 |
|---|---|
| Agent 循环和模型调度 | 读取准确的游戏状态 |
| Prompt、上下文、记忆和结构化输出 | 订阅游戏事件 |
| Schema 校验、完整输出重试和工具编排 | 通过游戏 API 执行已批准动作 |
| 多模态 Provider 调度 | 按需显示游戏原生界面 |
| ASR 与 TTS Provider 调度 | 返回动作结果和失败原因 |
| 麦克风采集、窗口捕获和音频播放 | 主机捕获不足时提供游戏渲染画面 |
| 密钥、日志、权限和版本更新 | 握手时提供游戏、版本和进程信息 |

游戏生态中已有的成熟通用组件可以留在游戏侧。例如星露谷的资源加载和宠物跟随分别交给 Content Patcher 与 TrinketTinker；小汤圆适配器只连接 Harness、游戏状态与 AI 展现。Harness 安装器负责发现、下载、校验和升级这些依赖，让用户仍然只需要一次对话安装。

Provider 密钥绝不进入游戏适配器。游戏协议中也不能出现具体 Provider 厂商名称。

## 产品必备能力

以下能力都有可用实现时，引擎才算完整：

1. 多模态理解。
2. 语音识别。
3. 语音合成。
4. 麦克风采集。
5. 音频播放。

同一个 Provider 可以实现多项能力，也可以为不同能力选择不同 Provider，并设置备用 Provider。强制要求的是能力可用，而不是绑定某个厂商。

## 运行流程

```text
主机麦克风 / 当前游戏窗口
             |
             v
Harness 媒体服务 -> ASR / 多模态 Provider
             |
             v
Agent + 上下文 + Schema 校验 + 工具编排
             |
             v
protocol/v1 -> 薄适配器 -> 游戏 API
             |
             v
TTS Provider -> Harness 音频播放
```

适配器还可以接收最终文本，在游戏内显示对话气泡或其他原生界面，但不负责录制麦克风，也不负责播放生成语音。

## 不放进适配器的内容

- 模型厂商 SDK 和 API Key。
- Prompt、角色人格和长期记忆。
- ASR、TTS 和模型 HTTP 请求。
- 麦克风设备及扬声器管理。
- JSON 修复、Schema 校验和模型重试。
- Agent 主循环和任务编排。
